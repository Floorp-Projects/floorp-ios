# Floorp iOS curated WebExtensions catalog

Status: **implementation inventory; not a publication approval.** The catalog
cannot be placed in an External TestFlight build until the sole maintainer's
candidate-bound P0 approval record and the managed signing record in [the
release gates](floorp-ios-webextensions-internal-catalog-release-gates.md) are
complete.

## What ships in the app

The release bundle contains only the following execution inputs:

```text
CuratedCatalog/
  Artifacts/Signed/catalog.json       signed canonical catalog (generated by managed signer)
  Artifacts/Signed/root-public-key.txt Ed25519 root public key
  Artifacts/<id>.fwea1         immutable, non-compressed reviewed resources
```

`Packages/`, `Review/`, source checkouts, ZIP/XPI/CRX files, private keys,
patch tooling, and remote artifact endpoints are build/review material and do
not belong in the iOS app. `artifactURL` in a signed bundled catalog is an
identity field only: the client maps its safe filename to the static bundle
resource and never fetches it.

On every launch the client verifies the catalog signature chain, audience,
expiry, sequence, revocations, every FWEA1 digest, manifest digest, inventory
digest, and closed MV3 preflight before showing an installable item. A failure
leaves catalog packages unavailable; it does not fall back to a ZIP, CRX,
remote URL, or a previous unsigned catalog.

## External TestFlight release contract

The ordinary main-branch Xcode Cloud dispatch is not catalog-candidate evidence.
`Floorp Curated Catalog TestFlight Candidate` is a separate, manual workflow
that accepts only a protected annotated `floorp-catalog-<40 lowercase commit SHA>`
tag whose name, tag commit, checked-out commit, and current `origin/main` HEAD all
match. It checks that source identity before making any
Apple credential available, then fails before it can start Xcode Cloud unless a
public-only verifier proves all of the following:

- `Artifacts/Signed/catalog.json` and `root-public-key.txt` exist, are
  canonical, have a valid root/leaf Ed25519 chain, and are currently valid;
- the root public-key SHA-256 matches the protected trust-anchor secret in the
  relevant `floorp-curated-catalog-candidate` or
  `floorp-curated-catalog-external-release` environment;
- the audience is exactly `app.floorp.Floorp` / `testflight`, and its minimum
  version and every package's `minimumFloorpBuild` equal
  `FloorpRelease.xcconfig`'s marketing version;
- the signed package records equal the reviewed `catalog-input.json`, contain
  exactly the current single package, and resolve only to the `.invalid`
  bundled artifact identity path; and
- every shipped FWEA1 is the exact signed digest, byte count, canonical
  inventory, manifest, and metadata-permission/host declaration, with no
  extra `.fwea1` beside the signed set.

The verifier has no private key and cannot make an arbitrary root key trusted:
the protected environment supplies the expected root-key digest independently
of the source tree. Missing signer output, a missing trust-anchor secret, a
version mismatch, or any tampering stops the workflow before the App Store
Connect mutation.

The candidate workflow passes that exact tag as Xcode Cloud's `sourceBranchOrTag`.
The source-controlled Xcode Cloud post-clone gate independently requires
`CI_GIT_REF`, `CI_TAG`, `CI_COMMIT`, the approved manual workflow and bundle ID to
agree with the tag suffix, then fetches current `origin/main` before `xcodebuild`.
It therefore rejects a moved/stale tag or automatic/wrong-workflow start before an
archive. The workflow also always waits for a terminal run and rejects a returned
`sourceCommit.commitSha` that differs from the checked-out/current-main tag
commit. GitHub tag immutability, Xcode Cloud manual-tag support, and the absence
of automatic external TestFlight exposure are environment gates, not facts
inferred from the source tree. The workflow does not
assign an external group or submit Beta App Review; a later, separately approved
operation must first bind the processed App Store Connect build back to that
verified Xcode Cloud run.

## Current curated inventory

All entries are immutable generation `g20260826-*` records produced from
[`catalog-sources.json`](../firefox-ios/Floorp/WebExtensions/CuratedCatalog/catalog-sources.json).
The current catalog contains only the reviewed Floorp compatibility build of
Dark Reader, not an unmodified upstream binary. Its exact upstream revision,
original input digest, license/notice digest, patch status, requested
permissions, host patterns, and private-profile capability are signed metadata.

| ID | User-facing name | Profile | Local function | Site scope |
| --- | --- | --- | --- | --- |
| `floorp.thirdparty.darkreader` | Dark Reader | content-script, action-storage | Local dark-theme transformation with bundled site configuration | Allowed HTTP(S) sites |

Dark Reader has no remote JavaScript, WASM, DNR subscription/list,
`update_url`, `webRequestBlocking`, dynamic code generation, or arbitrary
network fetch. Its configuration corpus is part of the immutable reviewed
artifact. A future curated extension may be added only after the same source,
compatibility, privacy, provenance, signing, and release review; changing the
current set requires a new signed catalog generation and candidate approval.

## Installation, profiles, and updates

- Initial installation starts site access as denied and requires product-owned
  native consent. An extension cannot manufacture that consent from JavaScript.
- Private browsing is a distinct ephemeral package installation. It starts
  with private site access denied and never copies normal-profile storage,
  DNR state, runtime state, or package files.
- Disable stops runtime/DNR/page hosts but retains data according to the
  documented policy. Explicit uninstall removes the package and its
  profile-owned data. Revocation stops runtime/DNR/page origins and never
  chooses an old generation as a fallback.
- Every replacement stays on the old generation until a native confirmation
  shows the exact digest and any added API permission or host pattern. A
  same-or-reduced-authority replacement receives the same confirmation; a
  signed catalog is never a substitute for it. All catalog, FWEA1, digest,
  revocation, and preflight checks must pass, and the replacement semantic
  version must be strictly newer than the installed package. An equal or older
  signed generation is rejected rather than becoming a rollback target.

## Required release material

Before signing, regenerate the deterministic review outputs with:

```sh
python3 scripts/webextensions/build_curated_catalog.py \
  --sources firefox-ios/Floorp/WebExtensions/CuratedCatalog/catalog-sources.json \
  --output firefox-ios/Floorp/WebExtensions/CuratedCatalog \
  --generation-prefix g20260826
```

The managed signer then uses `sign_curated_catalog.py` to create
`Artifacts/Signed/catalog.json` and `Artifacts/Signed/root-public-key.txt` from
`catalog-input.json`; it must not create, copy, print, or commit a private key.
The handoff rejects a dirty or
mismatched source commit, a catalog from another checkout, a mutable re-read of
the verified input, existing output or evidence files, and non-external/overlapping
evidence paths. Its review-only archive reader is bounded by compressed bytes,
member count, declared expanded bytes, target-file size, and duplicate target names.
It requires a successful, locally supplied archive verification for every declared
source-provenance record. The signing procedure, exact key IDs, sequence, expiry,
canonical digest, source-archive evidence, and candidate-bound sole-maintainer
P0 approval are release evidence. See
[ingestion](EXTENSION_INGESTION.md), [security model](EXTENSION_SECURITY_MODEL.md),
and [third-party provenance](THIRD_PARTY_EXTENSIONS.md).

The signing sequence itself is a release gate. Because the signer starts from a
clean exact commit and emits new public files, either the maintainer's managed
signer signs reviewed immutable inputs before the normal integration review, or
the reviewed input first reaches `main` and the resulting public signed outputs
go through a second normal review/CI integration. A direct push, a private key
in CI, or an unsigned TestFlight build is not a substitute for either sequence.
